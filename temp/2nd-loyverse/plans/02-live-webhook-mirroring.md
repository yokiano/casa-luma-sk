# Plan 02: Live Webhook Mirroring

## Outcome

After existing production receipt processing completes, selected eligible sales receive one isolated, best-effort attempt to create a corresponding sale in the second account.

A target failure is persisted and may trigger Telegram, but must never make production webhook processing fail.

## 1. Public module operation

The webhook integration calls one API such as:

```ts
considerAndMirrorReceipt(payload, primaryResult, { trigger: 'webhook' })
```

The module owns eligibility, cohorting, persistence, entity resolution, transformation, reconciliation, receipt creation, attempt finalization, and notification.

The webhook route must not know target entity or payload details.

## 2. Integration sequence

For each normalized webhook receipt:

1. Run existing `processReceiptWebhook()` unchanged.
2. Only after it returns, invoke the second-account module.
3. Persist/update transfer discovery and cohort decision before target work.
4. Return immediately for skipped or non-selected receipts.
5. Await one mirror attempt for a selected queued/failed receipt.
6. Catch every mirror error inside the module.
7. Persist attempt result before notification.
8. Return the original successful production webhook result regardless of target failure.

Do not use an unawaited promise inside a serverless request. V1 chooses an awaited end-of-webhook attempt because the user does not want worker/retry infrastructure yet.

If existing automation/validation throws after receipt ingestion committed, do not mirror from a `finally` block. Historical/manual discovery later recovers that receipt safely.

## 3. Eligibility and duplicate webhook behavior

Apply shared Plan 01 rules:

- skip refund receipts;
- skip cancelled receipts;
- skip unsupported true composites;
- use persisted deterministic 50% cohort.

Call the second module for primary `processed` and duplicate outcomes where safe. A duplicate webhook may resume a prior failed transfer, but a `succeeded` or `ambiguous` transfer must never blindly POST.

Defensively compare source fingerprints:

- same source version: idempotent no-op or eligible rerun;
- changed before target success: use latest persisted source snapshot;
- changed after target success: mark `source_changed`, notify/report, never create a second target sale.

## 4. Sale create projection

Build a dedicated writable payload.

### Include

- `store_id`: always `LOYVERSE_2_STORE_ID`;
- `receipt_date`: source receipt date, validated and normalized to UTC;
- `source`: fixed marker `casa-luma-2nd-loyverse`;
- `order`: deterministic digest marker from source receipt key;
- `note`: preserve source note where useful and append readable source receipt key;
- mapped target line `variant_id` and source quantity;
- allowed line price/cost overrides;
- source line note;
- mapped target taxes;
- mapped target ordinary discounts;
- mapped target modifier-option IDs and allowed price override;
- one target payment-type ID matched by name;
- writable payment timestamp when appropriate.

### Intentionally omit

- `customer_id`;
- `employee_id`;
- source item/category/entity IDs;
- source receipt number as target receipt number;
- `receipt_type`, `refund_for`, `created_at`, `updated_at`, `cancelled_at`;
- source-calculated totals and output tax/discount amounts unless the POST schema explicitly allows the relevant variable value;
- payment amount/details generated by Loyverse;
- loyalty points;
- tips and surcharges.

Add a concise code comment near omitted customer projection: sandbox analytics intentionally excludes customer identity and loyalty state.

## 5. Discounts

Ordinary discounts are feasible:

- ensure target discount exists through Plan 01;
- receipt-scoped discount goes in target `total_discounts` with correct writable scope/value fields;
- line-scoped discount is referenced on applicable target lines;
- fixed and variable amount/percentage fields must follow the official schema;
- never copy calculated output amounts as configuration values accidentally.

Point-based discounts are not treated as ordinary discounts because customers and target loyalty balances are absent. Mark those receipts unsupported or fidelity-reduced according to report policy.

## 6. Target marker and idempotency

Use:

```text
source = casa-luma-2nd-loyverse
order  = lv2:<stable digest>
note   = <source note> [Mirrored from <merchant_id>:<receipt_number>]
```

Before POST:

1. check Neon transfer status;
2. query target receipts by exact `source` and `order`;
3. zero matches: proceed;
4. one compatible match: record success without POST;
5. multiple matches: mark duplicate/ambiguous and notify.

Loyverse does not document an idempotency key or uniqueness for `order`. Neon plus marker reconciliation is the defense.

## 7. Attempt lifecycle

For a selected transfer:

1. atomically move `queued`/eligible `failed` to `processing` and allocate attempt number;
2. insert attempt start;
3. resolve entities;
4. build and validate request;
5. run marker reconciliation;
6. POST target receipt if absent;
7. validate target response;
8. save target receipt number and `succeeded`;
9. finalize attempt.

Concurrent claims for one source receipt must allow only one processor. Use a database transaction/conditional update, not process memory.

Failure classes:

- configuration;
- target authentication/authorization;
- source or target fetch;
- rate limit;
- ambiguous/incompatible entity name;
- unsupported receipt/discount/item;
- invalid create payload;
- target validation;
- target server/network;
- ambiguous POST outcome;
- source changed;
- duplicate target marker.

## 8. Ambiguous POST outcome

A timeout or disconnect after POST may mean Loyverse created the receipt.

Rules:

1. mark transfer and attempt `ambiguous`;
2. never immediately retry POST;
3. query target by exact source/order marker;
4. one compatible result becomes success;
5. no result remains ambiguous for manual reconciliation after an eventual-consistency delay;
6. several results become duplicate-target failure;
7. only an explicit reconciliation action may release the transfer for another POST.

This limited reconciliation is required even though v1 has no general retry scheduler.

## 9. Telegram policy

Only attempts with `trigger='webhook'` may notify Telegram.

Reuse `incidentReporter` with a dedicated code such as:

```text
SECOND_LOYVERSE_LIVE_TRANSFER_FAILED
```

Message includes:

- source receipt key/number;
- attempt ID;
- failed stage and safe error code;
- target HTTP status when safe;
- failed versus ambiguous classification;
- suggested next action.

Never include tokens, headers, full payloads, customer data, or unbounded responses.

Persist failure first. Telegram failure must not hide or replace the transfer failure.

Backfill/manual attempts never send these live alerts.

## 10. Performance boundary

V1 performs one awaited attempt after primary processing. Protect production behavior by:

- doing all primary work first;
- bulk-loading/caching inventories rather than per-line lookups;
- using low bounded API timeouts;
- catching target failures;
- recording stage timings;
- monitoring total webhook latency.

A POST timeout remains ambiguous, so timeout settings must not be so aggressive that they create routine uncertainty.

Escalation trigger for v2 worker/retry infrastructure:

- recurring webhook timeout;
- unacceptable p95 latency increase;
- repeated 429/5xx failures;
- queued/failed transfer backlog requiring frequent manual runs.

## 11. Feature flag and deployment

`LOYVERSE_2_MIRROR_ENABLED=false` by default.

When disabled:

- production behavior remains unchanged;
- optional discovery/cohort recording may be enabled separately only if explicitly designed;
- no target API write occurs.

Deployment order:

1. migration;
2. module/client code;
3. webhook integration still disabled;
4. historical validation through Plan 03;
5. enable live mirroring;
6. observe latency, success, and Telegram.

## 12. Tests

Focused tests:

- selected and non-selected receipts;
- refunds/cancelled unsupported;
- target configuration missing;
- target store forced;
- customer and employee omitted;
- item/variant/tax/modifier/discount IDs all target-scoped;
- payment type matched by name;
- target marker field generation;
- existing marker reconciles without POST;
- duplicate webhook cannot duplicate target receipt;
- concurrent claim allows one POST;
- source change after success cannot create another sale;
- POST timeout becomes ambiguous;
- live failure persists then notifies;
- Telegram failure does not alter production response;
- backfill trigger does not notify;
- target failure never changes successful production webhook HTTP behavior.

## Acceptance gate

The live plan is ready when a controlled selected sale can be mirrored once, all target failures remain isolated from production, duplicate and timeout cases cannot blindly POST twice, and live failures produce safe actionable Telegram notifications.
